# 04 — Internacionalização (i18n)

## Importante: isso não existia no site antigo

Ao ler o código original, o site descreve ter um sistema de i18n via `data-i18n`, mas essa busca não encontrou nenhuma ocorrência real no `index.html` nem no `gallery.js` — o site é 100% português, sem alternância de idioma. Este documento descreve um sistema **construído do zero** na Etapa 1, não uma "recriação" de algo que já existia.

## Por que `next-intl`

Existem duas formas de fazer i18n: uma solução caseira (Context do React + arquivos de tradução), ou uma biblioteca dedicada. Escolhemos **next-intl** porque é a biblioteca padrão do ecossistema Next.js App Router e resolve de fábrica coisas que teríamos que reinventar: roteamento por idioma (`/en/servicos`), geração estática por idioma, formatação de data/número por localidade — todas coisas que vão importar quando o site tiver e-commerce (preços, datas de evento) nas próximas fases.

## Como a URL decide o idioma

Configuramos em [`lib/i18n/routing.ts`](../lib/i18n/routing.ts):

```ts
export const routing = defineRouting({
  locales: ["pt", "en"],
  defaultLocale: "pt",
  localePrefix: "as-needed",
});
```

`localePrefix: "as-needed"` significa: o idioma padrão (`pt`) não aparece na URL (`/`, `/servicos`), só o idioma extra ganha prefixo (`/en`, `/en/servicos`). Isso preserva a URL raiz do site igual ao que já está indexado no Google hoje — não perdemos SEO trocando `/` por `/pt`.

## A peça que decide isso a cada request: `proxy.ts`

Antes de qualquer página ser renderizada, o Next.js roda [`proxy.ts`](../proxy.ts) (esse arquivo se chamava `middleware.ts` até a versão 15 do Next.js — a 16 renomeou a convenção para `proxy.ts`, e o código já nasceu com o nome novo). Ele olha a URL pedida, decide qual idioma se aplica, e passa essa informação adiante. É basicamente um "porteiro" que roda no servidor antes da página.

```ts
export default createMiddleware(routing);

export const config = {
  matcher: ["/((?!api|_next|_vercel|.*\\..*).*)"],
};
```

O `matcher` é uma exclusão: sem ele, o proxy rodaria para *toda* requisição, inclusive imagens e arquivos internos do Next — o que seria trabalho desnecessário. O padrão acima diz "rode em tudo, exceto rotas de API e arquivos com extensão" (imagens, CSS, etc.).

## Onde ficam os textos

Cada idioma tem um arquivo JSON próprio em `lib/i18n/messages/`, organizado por área do site — uma seção por página/componente (`Nav`, `Home.Hero`, `Home.About`, `Services`, `Budget`, `Footer`, etc.):

```json
// lib/i18n/messages/pt.json (trecho real)
{
  "Nav": { "home": "Início", "ariaLabel": "Navegação principal", ... },
  "Home": {
    "Hero": { "title": "Uma Experiência Única à Mesa", ... }
  },
  "Services": { "heading": "Nossos Serviços", "items": { "casamento": { "title": "Casamento" }, ... } }
}
```

As chaves precisam ser **idênticas** nos dois arquivos — só o valor muda. Hoje (após a auditoria pré-produção) são 154 chaves de cada lado — inclusive a Política de Privacidade inteira (`Privacy`) e a 404 (`NotFound`); validei isso com um script que compara as duas árvores de chaves recursivamente e não achou nenhuma diferença.

## Como usar num componente: `useTranslations` vs `getTranslations`

Existem DUAS formas de pegar o `t()`, e a escolha não é estética — é sobre onde o componente roda:

**`useTranslations`** (de `"next-intl"`) — para Server e Client Components **síncronos** (função normal, não `async`):

```tsx
import { useTranslations } from "next-intl";

export default function Hero() {
  const t = useTranslations("Home.Hero");
  return <h1>{t("title")}</h1>;
}
```

**`getTranslations`** (de `"next-intl/server"`) — para Server Components **assíncronos** (`async function`, geralmente porque a página precisa de `await params`):

```tsx
import { getTranslations } from "next-intl/server";

export default async function ServicosPage({ params }) {
  const { locale } = await params;
  const t = await getTranslations("Services"); // note o await
  return <h1>{t("heading")}</h1>;
}
```

**Por que a distinção importa:** `useTranslations` tem "use" no nome porque segue as regras de Hooks do React — e uma dessas regras (reforçada pelo ESLint) é que hooks não podem ser chamados dentro de uma função `async`. Bati nisso literalmente durante a auditoria: as páginas de Serviços e Orçamento viraram `async function` (para poder dar `await params`), e o ESLint acusou `useTranslations` como erro — a correção foi trocar para `getTranslations`, que foi desenhado exatamente para esse caso.

## Renderização estática (SSG) e `setRequestLocale`

Esse mesmo `await params` tem outro efeito colateral, mais sutil: por padrão, qualquer página cujo conteúdo dependa de um parâmetro dinâmico (como `[locale]`) só pode ser **pré-gerada em build** (SSG, rápido, servido puro do CDN) se o Next.js conseguir provar, com certeza, que já sabe todos os valores possíveis daquele parâmetro. `generateStaticParams` (em `layout.tsx`) já informa isso — mas descobrimos, auditando o resultado do `next build`, que as 6 combinações de rota×idioma continuavam marcadas como **dinâmicas** (`ƒ`, renderizada a cada request) em vez de estáticas (`●`).

A causa: `useTranslations`/`getTranslations`, quando chamados sem um `locale` explícito, descobrem o idioma atual através de um mecanismo interno que o Next.js trata como "dependente da requisição" — o que basta para desativar a geração estática da página inteira, mesmo que o idioma já estivesse decidido pela própria URL.

A correção é chamar `setRequestLocale(locale)` (de `"next-intl/server"`) o quanto antes — no layout e em cada página — **antes** de qualquer `useTranslations`/`getTranslations`. Isso avisa o Next.js: "o locale já está resolvido, pode gerar essa página em build":

```tsx
// app/[locale]/layout.tsx
const { locale } = await params;
if (!hasLocale(routing.locales, locale)) notFound();
setRequestLocale(locale); // precisa vir antes de qualquer tradução ser lida
```

Resultado confirmado no `next build` depois da correção: as 6 páginas passaram de `ƒ` para `●` (HTML estático, pré-gerado, servido do CDN da Vercel sem re-renderizar no servidor a cada visita). Hoje são 8 (a Política de Privacidade entrou depois).

## Detecção de idioma e o cookie `NEXT_LOCALE`

Quem acessa `/` com o navegador em inglês (`Accept-Language: en`) é redirecionado para `/en` pelo proxy. Quando o visitante troca de idioma, o next-intl grava o cookie `NEXT_LOCALE` (de sessão, `SameSite=Lax`, valor `pt` ou `en`) para lembrar a escolha. É o único cookie do site e está declarado na Política de Privacidade (ver [`07-protecao-de-dados.md`](./07-protecao-de-dados.md)).

## Página 404 traduzida

Qualquer caminho que não seja uma página (ex: `/xyz`, `/en/abc`) cai em [`app/[locale]/[...rest]/page.tsx`](../app/[locale]/[...rest]/page.tsx), que chama `notFound()`. Isso dispara [`app/[locale]/not-found.tsx`](../app/[locale]/not-found.tsx) **dentro do layout do idioma**, com menu, rodapé, `lang` certo e texto traduzido. Sem a rota pega-tudo, o Next.js usaria a 404 padrão dele, em inglês e fora do layout.

## Textos com link no meio: `t.rich`

Quando uma frase traduzida tem um link no meio ("Li e estou ciente da **Política de Privacidade**"), a tradução marca o trecho com uma tag e o componente decide o que ela vira:

```json
"privacyConsent": "Li e estou ciente da <link>Política de Privacidade</link>"
```

```tsx
t.rich("privacyConsent", {
  link: (chunks) => <Link href="/privacidade">{chunks}</Link>,
})
```

Assim a ordem das palavras pode mudar em cada idioma sem quebrar o link, e o HTML nunca sai do arquivo de tradução (não existe risco de injetar markup por ali).

## Como adicionar um texto novo (fluxo de trabalho)

1. Adiciona a chave em `lib/i18n/messages/pt.json` **e** em `en.json`, com o mesmo caminho.
2. Usa `t("chave")` no componente (`useTranslations` ou `getTranslations`, conforme a regra acima).

Se uma chave existir em `pt.json` mas não em `en.json` (ou vice-versa), o next-intl avisa em tempo de desenvolvimento — não é um erro silencioso.
